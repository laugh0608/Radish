# 公开社区发现应用结构

> Radish 纯 Web 默认入口 `/discover` 的公开内容流说明。
>
> **最后更新**: 2026.08.03

## 定位

`/discover` 是普通浏览器根入口 `/` 的公开社区发现页，承接未登录、轻登录和外链回流用户的第一跳阅读。

当前它属于公开内容壳层，不等同于 WebOS 工作台，也不等同于完整推荐系统或个人圈子。

`2026-07-04` D61 后，`/discover` 承接旧 `public-web-unified-experience.pen` 中 `P01 - Public App Home` 与 `P02 - Discover Content Stream` 的发布前职责：首屏保留产品级 `Radish / 公开入口` 头部、紧凑公开脉搏、真实帖子讨论流和公共内容亮点；移动端在真实内容前提供搜索 / 筛选快捷入口，但不把页面改成营销首页、路由矩阵或大面积说明页。

`2026-08-03` 起旧文件只读留档，后续视觉裁决进入 `Docs/frontend/design-sources/radish-web-family-ui-v1.pen` 的 `R1-P01`；本页与当前代码继续负责功能、入口、数据和停止线。

`R1-P01` 当前处于独立业务页面复核阶段。首轮复核确认原“论坛热帖主流 + 相关内容 rail”过度压缩了社区首页：真实接口读取的是最新帖子而非热帖，且分类、标签和其他结构化社区内容没有形成清楚层级。当前设计目标调整为“最新讨论 + 分类浏览 + 社区正在发生 + 热门主题 + 相关内容”，仍不恢复旧稿中的混合推荐流，也不新增推荐算法、权限或状态机。

## 内容流范围

当前页面复用现有公开数据，不新增推荐读模型：

- 最新讨论：`getPostList(..., 'newest')` 读取公开帖子，页面展示前 `5` 条 `PostCard(publicCompact)`；普通帖、问答、投票和抽奖沿现有结构化状态共同出现，卡片优先使用 `Post.PublicId` 路径，并输出可新标签打开的真实 `href`。
- 分类浏览：`getTopCategories` 读取顶级分类，PC 展示最多 `6` 项、mobile 展示紧凑入口；分类表达单一主归属，并进入 `/forum/category/:categoryId`。
- 社区正在发生：并行复用现有帖子列表筛选，分别取得一条待回答问题和一条进行中投票；`getFixedTags` 提供社区新闻、社区活动、公告等稳定栏目入口。任一局部读取失败不得清空最新讨论或其他社区区块。
- 热门主题：`getHotTags` 读取最多 `6` 个标签，作为独立主题区，不改变最新讨论排序。
- 相关文档：只读取公开文档列表首项，在右侧“相关内容”中链接 `/docs/:slug`；无数据或失败时回退到公开文档列表入口。
- 相关商品：只读取公开商品首项，在右侧“相关内容”中链接 `/shop/product/:productId`；无数据或失败时回退到公开商品列表入口。
- 榜单入口：右侧固定指向公开榜单，不在 `/discover` 内复制榜单筛选或排名逻辑。
- 公开主页入口：从帖子作者、榜单或作者入口进入 `/u/:identifier`，其中 `identifier` 优先为 `User.PublicId`，并输出真实公开 `href`。
- 移动公开任务入口：在 `390px` 级视口下提供搜索、全部、最新、问答、热门；这些入口只复用既有 `/forum/search`、`/discover`、`/forum`、`/forum/question` 和 hottest 列表路由。

首批不包含：

- 完整推荐算法
- 完整个人圈子 / 关注流
- ActivityPub / WebFinger / Mastodon 客户端能力
- 登录后工作台治理动作
- 订单、背包、账号设置或 Console 排障入口
- 统一搜索 API、跨类型推荐读模型或公开聊天室路由

### 分类、标签与结构化状态

- 分类是帖子的唯一主归属，使用品牌柔底、无 `#` 的独立 chip，并进入公开分类页。
- 标签是一篇帖子可拥有的横向主题，使用较轻的 `#标签` chip，并进入公开标签页；标签不得冒充分类，也不承担帖子状态。
- 问答、投票、抽奖、精华和置顶属于结构化状态，继续使用状态 chip；它们与分类、标签分组排列，不复用同一视觉样式。
- `PostCard(publicCompact)` 的展示顺序固定为“分类 → 标签 → 结构化状态”，mobile 可以换行但不能混成一组无差别胶囊。

## `P3-10-D` / `R1-P01` 信息结构口径

`/discover` 后续整理目标不是重做品牌首页，而是把已落地的公开内容流继续压实为“打开即可阅读”的社区起点。

### 页面层级

页面信息层级按以下顺序稳定：

1. 公共壳层头部：只承担品牌返回、公开发现、登录态圈子和历史工作台入口；不承载筛选器、推荐解释或工作台动作。
2. 移动任务区：只在 mobile 前置搜索与“全部 / 最新 / 问答 / 热门”筛选；PC 继续由页面主内容承担筛选与阅读起点。
3. 紧凑起读区：直接展示“发现社区动态”标题、进入论坛、搜索社区和复制链接；不添加描述性副标题，也不扩成营销 hero。
4. 分类浏览：在进入帖子流前提供顶级分类入口，让“内容归属”与后续 `#标签` 主题明确分层。
5. 最新讨论：作为页面主流展示最新公开帖子，不再把 `newest` 数据命名为“热帖”。
6. 社区正在发生：以紧凑卡片展示待回答问题、进行中投票与社区新闻 / 活动 / 公告入口，不和最新讨论做跨类型统一排序。
7. 热门主题：单独展示热门 `#标签`，负责横向主题发现。
8. 相关内容：文档、商品、榜单和登录参与提示保持次级，不冒充社区主内容。
9. 状态与反馈：最新讨论使用共享 `WebStateSlot`；其他社区区块局部失败时保留其余内容，复制链接结果留在动作附近。

D61 后的首屏实现要求：

- PC 首屏使用产品头部 + 紧凑起读区 + 分类浏览 + 最新讨论主流；社区正在发生、热门主题与相关内容形成有主次的辅助区，不再使用大型验收型 hero、无差别入口矩阵或混合推荐流。
- 移动首屏优先展示搜索 / 筛选快捷区、分类入口和最新讨论，随后按“社区正在发生 → 热门主题 → 相关内容 → 参与提示”单列落位，底栏前应看到实际内容，不以说明卡替代内容流。
- 公共页头右侧使用登录 / 登录态入口和工作台动作，文案保持“发现 / 公开入口”语义，不回退为 WebOS 或内部验收术语。

### 首屏内容密度

- PC 首屏应至少露出公共头部、首屏引导、内容流标题和第一组真实内容卡片的顶部。
- 移动首屏应优先保证第一张可读内容卡片尽早出现；头部次级动作可以继续图标化，说明型卡片不应连续堆叠。
- hero / guide / summary 只能保留帮助用户理解内容来源的最小信息；如果后续改版需要新增大面积引导、插画或营销文案，必须先进入设计源文件评审。
- 空态、加载态和部分失败态必须继续说明内容来源、下一落点和公开边界，但不能用长文案替代真实内容。

### 内容卡片优先级

首批卡片排序仍以现有公开数据为边界：

1. 最新讨论只按现有 `newest` 排序，不在客户端伪造热度或推荐顺序。
2. 待回答问题与进行中投票各自使用现有类型和状态排序，只在“社区正在发生”中独立展示，不并入最新讨论统一排名。
3. 分类、固定栏目和热门标签只承担导航与数量信号，不参与帖子排序。
4. 公开文档、商品和榜单只作为相关内容与列表回流，不进入社区主列表排序。

若需要跨类型排序、个性化、推荐解释、置顶、去重或分页续读，应先设计 feed API / 读模型；不要在 `PublicDiscoverApp.tsx` 内继续堆叠临时排序和来源拼装规则。

### 与相邻页面分工

| 页面 | `/discover` 需要交接的内容 | 不应接管的职责 |
| --- | --- | --- |
| `/forum` / `/forum/post/:id` | 公开帖子入口、标签入口、轻互动登录回流 | 帖子详情、评论树、点赞、投票、编辑、治理 |
| `/docs` / `/docs/:slug` | 公开文档入口和阅读回流 | 文档目录治理、搜索完整体验、编辑 |
| `/shop` | 商品公开浏览入口 | 购买、订单、背包、资产校验 |
| `/leaderboard` | 榜单入口和公开个人页线索 | 榜单类型完整筛选和管理 |
| `/circle` | 登录态关系链复访入口 | 关注流、粉丝列表、私域动态、推荐算法 |
| `/me` | 登录态个人状态复访入口 | 完整个人中心、完整钱包、账号设置 |

### 代码进入条件

进入 `/discover` 页面结构代码改造前，应先满足：

- 不改变 `/discover` 公开集合页 canonical、OpenGraph、JSON-LD 和 sitemap 口径。
- 不把来源返回状态写入 URL、分享链接或 head 输出。
- 不新增推荐系统、关系链私域数据、登录后工作台操作或 Console 入口。
- 不破坏普通点击保留来源返回、新标签打开使用真实公开 `href` 的契约。
- PC 与移动两种视图都能证明没有横向溢出、按钮文字挤压或首屏只剩说明文字。

## URL 与来源返回

- `/discover` 本身是公开集合页，canonical 和分享链接不携带工作台状态。
- 从 `/discover` 进入 forum / docs / shop / leaderboard / 公开主页后，返回动作应优先回到社区发现页和原阅读上下文。
- 公开详情来源返回使用浏览器 `history.state`，不写入 URL query、canonical、OpenGraph 或 sitemap。
- 内容卡片必须保留真实公开 `href`：普通点击可以同时写入 `history.state` 保存来源返回；新标签打开、复制链接、浏览器地址栏、canonical 和结构化数据只依赖公开真实路径。
- 普通浏览器根路径 `/` 当前进入 `/discover`；Tauri / WebOS 工作台仍保留 `/desktop`。

## 公开 head 与结构化数据

`/discover` 使用公开壳层统一 head helper 和结构化数据 helper：

- 作为公开集合页输出 `CollectionPage` JSON-LD。
- canonical 使用公开 Gateway origin。
- 分享链接只保留公开路径，不携带来源状态、窗口参数或登录后上下文。

## 维护约束

- 内容卡片应优先使用公开标识和公开路径；旧 LongId 只作为兼容打开或内部接口参数。
- 页面可以增加登录后轻互动入口，但不能把工作台动作搬进首屏内容流。
- 新增内容来源前应先确认已有公开 API、公开 head、移动 / PC 布局和来源返回语义。
- 从 `/discover` 进入 `/circle` 或公开详情后再继续打开内容详情时，来源交接只允许使用当前标签页的一次性状态；不得把来源状态固化进分享 URL 或 SEO 输出。
- 若后续需要跨类型排序、推荐解释或个性化，应先单独设计 feed API 或读模型，不在当前页面内堆叠 ad hoc 排序逻辑。

## 验证要点

- PC 下 `/discover` 能区分分类、标签和结构化状态，并展示分类浏览、最新讨论、社区正在发生、热门主题及次级相关内容；mobile 下搜索 / 筛选前置且各区块按单列顺序落位，不退回 WebOS Shell。
- 卡片进入 forum / docs / shop / leaderboard / 公开主页后，返回语义稳定。
- 公开帖子卡片优先进入 `/forum/post/:publicId`。
- 公开主页入口优先进入 `/u/usr_...`，旧 LongId 仅保留兼容。
- 卡片右键打开新标签、复制链接和普通点击都能进入同一公开详情；只有普通点击额外保留来源返回状态。
- head、canonical、OpenGraph 和 JSON-LD 不携带登录后状态或来源状态。
