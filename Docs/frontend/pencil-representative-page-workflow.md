# Pencil 代表页协作流程

> 日期：2026-07-30（Asia/Shanghai）
>
> 状态：当前 UI 设计与实现协作规则
>
> 适用范围：Radish Web、Console 与后续 Flutter 高价值移动路径

## 1. 核心结论

Radish 后续采用“代表页驱动设计”，不再要求把每条路由、每个状态和每次文案变化都同步为完整 Pencil 页面。

Pencil 的职责是确认高影响、可复用的视觉契约：

- 共享壳层和布局范式；
- 信息层级、组件关系和交互密度；
- 关键状态及 PC / mobile 的结构变化；
- 新视觉模式在一个真实页面中的组合效果。

Pencil 不是功能清单、产品文案、权限矩阵或代码现状的完整镜像。相似页面在继承已确认视觉契约后可直接实现，再通过真实页面截图和代码侧验证复核。

## 2. 真相源分工

| 内容 | 权威来源 | Pencil 职责 |
| --- | --- | --- |
| 功能范围、按钮动作、权限、接口、路由、状态机 | 功能专题、`Docs/`、API 契约与当前代码 | 只展示已确认能力，不自行发明功能 |
| 产品文案与 i18n | 当前文案专题、locale 资源与代码 | 只保留影响层级或布局的代表文案与长文本样例 |
| 家族视觉语义 | family-ui、[Radish UI 差异附录](/frontend/ui-addendum)与主题 token | 组合和验证视觉规则 |
| 共享组件与壳层 | `@radish/ui`、共享壳层代码、`web-ui-foundation.pen` | 固定合法视觉变体 |
| 页面结构与响应式关系 | 页面族说明、代表画板与当前代码事实 | 固定代表结构和 PC / mobile 转换 |
| 最终可执行行为 | 实际代码、自动化测试与运行态复核 | 不替代实现验收 |

发现冲突时按以下方式处理：

1. Pencil 出现未获批准的按钮或功能：删除或标为概念，不据此直接实现。
2. 已批准功能或文案变化但视觉契约未变：更新文档和代码，不要求机械回写 Pencil。
3. 代码偏离已确认的代表视觉契约：优先修正代码。
4. 代码事实证明原设计边界错误：先更新专题或实现契约，再决定是否更新代表画板。

## 3. 什么是代表页

代表页不是“访问量最高的页面”或“产品首页”的同义词，而是：

> 能够确定一套可复用 UI 语法，并且设计错误会影响多个页面、核心任务或高风险操作的最小真实页面。

选择单位是“页面类型 / 交互范式”，不是路由数量。一个代表页可以覆盖多个使用相同壳层、组件组合、状态结构和响应式转换的派生页面。

### 3.1 自动升级条件

命中任一条件时，默认升级为完整代表页：

- 引入新的共享壳层、导航或布局范式；
- 涉及高风险权限、不可逆写操作或多步骤确认；
- PC 与 mobile 需要不同的交互模型，而不只是换行或堆叠；
- 改变跨 Public、Private / Author、Console 复用的组件契约；
- 文档、现有代码和目标视觉之间存在尚未解决的结构冲突。

自动升级条件按当前 UI 批次的目标变化判断，不按页面已有功能机械判断。已有高风险动作若在本批明确保持行为和结构不变，并能完整继承已确认契约，可降为 R2 / R3；关键动作区仍必须进入继承说明和真实页面复核。

### 3.2 六维评分

未命中自动升级条件时，按下表每项 `0～2` 分评估：

| 维度 | `0` | `1` | `2` |
| --- | --- | --- | --- |
| 业务关键度 | 辅助展示 | 常规任务 | 核心任务或高风险动作 |
| 布局独特性 | 完全继承 | 明显变体 | 新壳层或新页面类型 |
| 状态复杂度 | 单一稳定态 | 少量空态 / 错误态 | 权限、冲突、实时或多步骤状态 |
| 复用影响面 | 单页面 | `2～3` 个页面 | `4+` 页面或共享层 |
| 响应式风险 | 直接堆叠 | 顺序或密度变化 | 交互模型发生变化 |
| 现状不确定性 | 代码与目标清楚 | 存在局部分歧 | 结构或功能边界尚未对齐 |

分级规则：

| 结果 | 设计方式 |
| --- | --- |
| 自动升级或总分 `≥ 7` | R1：完整代表画板，覆盖 PC / mobile、关键状态和真实组件关系 |
| 总分 `4～6` | R2：只画关键区块、状态带、交互序列或响应式差异，不创建完整路由镜像 |
| 总分 `≤ 3` | R3：继承既有代表页直接实现，完成后通过真实页面截图复核 |

评分用于避免遗漏和控制规模，不替代产品判断。若评审仍无法就结构达成一致，页面应升级而不是用低分绕过设计。

## 4. 派生页面的继承条件

R3 页面只有同时满足以下条件才能直接实现：

1. 能明确写出继承的代表画板或共享基座；
2. 不新增布局范式、共享组件或全局交互；
3. 功能、按钮、权限、状态和接口已有权威定义；
4. PC / mobile 行为能够复用已确认的转换方式；
5. 允许的局部差异可以在任务说明或页面专题中清楚列出。

实现前记录一份轻量继承说明：

```text
代表画板：
复用壳层 / 组件：
本页局部差异：
必须覆盖的状态：
mobile 转换：
```

无法填写上述内容，或实现中出现新的结构问题时，应停止扩张并将该页面升级为 R1 / R2。

## 5. 标准协作流程

### 5.1 代码事实审计

进入 Pencil 前先读取当前实现和直接相关专题，至少确认：

- 真实路由、入口和返回语义；
- 已有组件、按钮、动作与权限；
- 加载、空态、错误、不可用、冲突和成功状态；
- PC / mobile 当前结构与已知问题；
- 本批明确不改变的功能边界。

事实审计写在 Markdown 专题或任务说明中，不把完整功能清单复制进 `.pen`。

### 5.2 代表页裁决

1. 按页面类型归组，而不是按路由列画板。
2. 先应用自动升级条件，再完成六维评分。
3. 明确 R1 / R2 / R3、对应设计源和继承关系。
4. 代表页集合确认后再修改 Pencil，避免边画边扩范围。

### 5.3 Pencil 设计

- 一个画板优先并置 PC / mobile 和少量关键状态，避免为每个状态复制完整页面。
- 四主题由共享 token / 状态矩阵和少量代表面验证，不复制四套完整页面族。
- i18n 使用真实短文案与长文本压力样例；locale 资源仍是文案真相源。
- 共享组件先在 `web-ui-foundation.pen` 确认，业务设计源只组合合法变体。
- 只读取和修改当前任务相关节点；阶段审阅优先使用目标节点截图和轻量评审板，不默认加载整个设计源。

### 5.4 实现与派生

1. 先实现 R1 代表页和共享组件。
2. 用 PC / mobile 真实截图确认视觉契约可落地。
3. R2 按确认的关键区块或状态进入实现。
4. R3 页面按继承说明成组实现，不追加重复画板。
5. 若派生实现暴露新页面类型、关键状态或响应式模型，再升级并补设计。

### 5.5 复核与回写

复核以真实代码为对象，覆盖：

- 代表页与设计契约是否一致；
- 派生页是否正确继承，是否出现平行组件；
- PC / mobile、长文本、关键主题和可访问状态；
- Pencil 中是否仍有未实现或未批准功能。

只有共享视觉契约、代表页面结构或响应式模型发生变化时才回写 Pencil。普通文案、字段、低风险按钮和等价功能变化不要求逐项同步画板。

## 6. 设计源规模控制

- 既有大型 `.pen` 保留为历史设计资产，不在本轮一次性重写或拆除。
- 后续停止按路由和功能点持续新增完整页面镜像。
- 每个阶段只维护当前代表画板和必要状态；废弃方案不长期堆叠在活动工作区。
- 同类页面优先共用一张代表画板和 Markdown 继承表。
- 需要阶段级横向比较时，可使用轻量评审板或导出截图，不复制完整可编辑页面。
- 拆分、归档或删除历史画板属于独立设计源治理任务，必须先盘点引用关系，不在功能批次中顺手处理。

## 7. Radish 当前代表类型

F4-R C-1A 代码事实审计已经完成，最终裁决见[F4-R C-1 代表页代码事实审计](/frontend/f4-r-representative-page-audit)。首轮采用一个基础矩阵和六类完整页面类型：

1. 共享组件、状态、主题和壳层矩阵；
2. Public 内容流；
3. Public 详情与互动；
4. Author 编辑 / 发布；
5. Private 消息或列表—详情工作台；
6. Console 表格 / 明细；
7. Console 案件治理 / 审计。

设置页、相似详情和低频表单默认从这些类型继承；必要差异只维护 R2 区块或状态。只有评分或自动升级条件证明现有类型不足时，才新增完整代表画板。

Flutter 在 Web 视觉契约稳定后单独判断原生代表路径，不复制 Web 画板；WebOS 只维护历史兼容，Tauri 不进入设计矩阵。

## 8. 完成定义

一个 UI 批次不以“所有页面都有 Pencil 画板”为完成条件，而以以下结果为准：

1. 代表类型、评分和继承关系可追溯；
2. R1 / R2 已完成必要 Pencil 设计与审阅；
3. 功能、文案、权限与代码事实没有未解决冲突；
4. 代表页已在代码中落地，派生页没有新增平行视觉体系；
5. PC / mobile 真实页面复核通过；
6. 设计源没有因重复路由、主题、文案或状态产生无必要膨胀。
