# 普通 Web 频道消息发送与手动重试联验

2026-11-27 在 OrbStack 验证普通 Web 候选 `172638e9`。PC 和移动端各在同一频道发送三条独立测试消息。六个原请求在手动重试后均只对应一条 PostgreSQL 消息和一次 Chat Hub 广播。两个浏览器都复现了回执先到时页面误报失败的问题。[会话验收矩阵](../features/auth-session-overnight-recovery-plan.md#修复验收)

## 两端实测

PC Chromium 使用 1920 × 1080 视口，移动 Chromium 使用 390 × 844 视口并模拟触屏。两份浏览器资料分别登录，经 HTTPS Gateway 使用真实频道发送入口。每次手动重试前观察 16 秒，核对发送请求次数、页面消息 ID、重试入口、Hub 回执，以及 PostgreSQL 中的 `id`、`clientrequestid` 和行数。

| 首次发送场景 | 点击重试前，两端观察一致 | 手动重试后，两端观察一致 |
| --- | --- | --- |
| 首次发送缺少认证，API 返回真实 `401` | 数据库 0 条。凭据恢复返回 `200`，页面允许重试，期间只发出一次发送请求 | 发送返回 `200`，写入 1 条，收到 1 次回执 |
| 消息已落库，Hub 回执先到，再丢弃 HTTP 成功响应 | 已在页面看到持久消息 ID。丢弃响应后，页面将同一消息改回失败并显示「重试」。数据库已有 1 条，期间没有自动重发 | 返回原持久消息 ID。数据库仍为 1 条，回执总数仍为 1 |
| 消息已落库，暂缓该条 Hub 回执，再丢弃 HTTP 成功响应 | 页面保留待重试的失败项。数据库已有 1 条，期间没有自动重发 | 返回原持久消息 ID，再放行原回执。数据库仍为 1 条，页面显示 1 条，回执总数为 1 |

六次手动重试均复用原 `clientRequestId` 和相同的发送字段。每端刷新页面后，三条消息各出现一次，ID 与数据库一致，全程停留在原频道，无额外登录。另有一条 PC 预检样本用于校正请求比对方法，正式六组均按解析后的 JSON 字段和值比较，同一对象的字段顺序不影响结果。

本轮从本地缓存构建五个候选镜像，Gateway 仅发布 `127.0.0.1:35443`，一次性 PostgreSQL 的 `dbmigrate apply` 与 `verify` 均通过。结束后项目容器、卷、网络计数分别由 6、4、1 降至零，五个候选标签、证书及浏览器资料已清理，端口已释放。

## 页面修复与验证

此前页面在发送请求失败时，直接把发出请求时保存的本地消息重新写入列表，即使 Hub 已经用服务端消息替换了它也会显示「重试」。修复后，失败处理读取当前频道中的发送状态，只在同一请求仍待确认时标记失败并提示用户。历史补拉取得持久消息时，同一请求的旧本地状态也不能覆盖它。手动重试继续使用原请求标识和内容。[聊天失败恢复规则](../features/chat-frontend.md#失败恢复与诊断)

定向回归覆盖回执先到、失败先到后手动重试、迟到回执清除失败状态、历史补拉、其他发送者的同键回执和已移除的本地项。HTTP 层覆盖连接中断后的显式重试，API 层覆盖已落库消息重试时复用原消息且跳过重复广播。

普通 Web 与共享 HTTP 的测试分别通过 582 项和 85 项，频道消息控制器与发送服务的 17 项定向测试通过。普通 Web 构建通过。修复后的 PC 和移动端页面效果待新候选隔离复验。
