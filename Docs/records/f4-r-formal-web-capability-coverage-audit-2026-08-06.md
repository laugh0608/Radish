# F4-R 正式 Web 能力覆盖复核

> 日期：2026-08-06（Asia/Shanghai）
>
> 状态：静态复核完成；四项推进决策已于 2026-08-06 确认，不包含运行时代码或服务启动
>
> 范围：正式 Web、仍在仓库中的 WebOS 历史实现、已完成专题与现有 API / Service；不是新一轮全量视觉审计

## 1. 结论

当前问题不是“第一次 UI 重构的大部分功能都没有做完”，而是当时的正式 Web 迁移按批次关闭，并明确把少数复杂能力留在后续。消息、通知、商店、经验、文档治理、公开发现、排行榜等页面族已经由正式 Web 直接复用或完整承接；论坛详情参与能力、基础资料设置和萝卜资产的部分能力仍存在正式入口覆盖差异。

这次 R1-P02 评审暴露出的根因是流程缺口：后续代表页审计准确核对了正式 Web 当前代码，却没有再次验证“历史实现中仍有价值的能力是否已经迁移”。当 WebOS 被正确排除出正式视觉设计范围后，当年的“延期迁移”又被误当成长期产品停止线。

因此：

1. R1-P02 能力审计冻结解除，按已确认的产品完整清单恢复代表设计；正式实现仍等待设计确认。
2. 论坛点赞、reaction、回帖的回帖等已有 API 与实现不得被当作新功能，确认接入正式 Web。
3. Console 管理能力、WebOS 工具入口和正式社区能力按职责判断，不追求机械页面对等。
4. F4-R 后续代表页进入设计前增加能力覆盖门禁；本批完成后的视觉工作默认继承新家族 UI 基线优化更新，不从零重设计。

## 2. 判定口径

| 分类 | 含义 | 后续处理 |
| --- | --- | --- |
| 已承接 | 正式 Web 已直接复用实现，或已有等价正式入口 | 不再扩审，只按代表页更新视觉 |
| 待接入 | API、权限和历史实现均存在，但正式 Web 未接线 | 先确认正式入口，再纳入对应 R1 / R2 |
| 待裁决 | 能力真实存在，但涉及高风险写入、复杂类型或产品定位 | 单独作产品决定，不随视觉稿暗中迁移 |
| 历史保留 | 仍适合作为 WebOS / 工具 / 调试入口，不属于正式社区 | 保留历史，不要求视觉对等 |
| 已废弃 | 产品明确不再需要，允许后续删除实现与说明 | 必须有明确退役结论，不能靠入口缺失推定 |

“正式 Web 当前没有按钮”只能证明没有接入，不能单独证明能力已经废弃。

| Forum 发帖、问答回答、编辑与版本 | 正式 Web 已覆盖发帖、回答生命周期、作者编辑与版本查看 | WebOS 仍保留旧入口 | 已承接；继续以正式 Web 为权威 |

## 4. 需要接回的论坛详情能力

当前共享实现已经提供以下能力：

- 帖子点赞与帖子 reaction 写入；
- 父回帖、子回帖的点赞与 reaction 读写；
- 对回帖继续回复；
- 作者删除帖子、轻回应和回帖；
- 投票提交 / 关闭与抽奖开奖等类型操作。

`ForumApp.tsx` 已将这些回调传给 `PostDetailContentView`，而 `PublicForumDetail.tsx` 当前只展示帖子 reaction 汇总，并没有把同一组普通读者参与回调完整传给共享回帖树。R1-P02 不是在请求新增点赞、reaction 或评论回复能力，而是在决定既有能力如何回到正式产品主线。

建议按职责拆分：

1. **普通读者核心参与**：帖子点赞 / reaction、父子回帖点赞 / reaction、回帖的回帖，纳入 R1-P02 正式 Web 产品边界。
2. **作者管理动作**：帖子、轻回应和回帖删除继续保留既有权限，只进入作者菜单和关键状态，不占普通读者代表画板的主要视觉层级。
3. **类型专属操作**：投票和抽奖继续保留能力，但用普通帖子之后的类型差异状态收口，不改变本轮“登录普通读者 + 普通帖子”代表身份。
4. **命名与层级**：页面统一称“回帖”；神评属于父回帖，沙发属于子回帖；轻回应、回帖赞赏和表情回应均保持克制，不扩成第二个正文流。

## 5. 个人资料与资产差异

### 5.1 基础资料设置

正式 `/me` 已经覆盖大部分个人内容和治理任务，但没有资料编辑、头像管理和时区偏好入口；这些能力仍存在于 WebOS `ProfileApp / UserInfoCard`，相关 API 也仍在使用。

建议把“基础资料编辑 + 头像 + 显示时区”认定为正式 Web 应承接的普通账号能力，并在后续 Private / Author 代表页范围中确定入口。登录密码、支付密码等安全操作不与基础资料表单混为一个视觉任务。

### 5.2 萝卜资产

正式 `/me/assets` 已承接余额与交易记录；WebOS Radish Pit 的转账、安全状态 / 支付密码、安全日志和统计是真实实现，不是静态占位。但这些能力涉及资金写入、身份验证和产品激励定位，不能因“代码已有”就在 F4-R 视觉批中直接迁移。

建议本轮保持正式资产概览与记录不变，并在社区核心互动恢复后建立独立产品裁决：

- 若继续保留转账和资产安全能力，应迁移到正式 Private Web 并补安全与响应式验收；
- 若产品不再需要，应明确退役 API、历史 UI 与文档；
- 本轮已确认独立后置；在后续迁移 / 退役裁决前不能算已完成，也不能算已废弃。

## 6. 对 F4-R 的影响

1. R1-P02 先以确认后的普通帖子完整能力清单重新收敛唯一 PC 方案；用户确认后才继续 Mobile 和代码实现。
2. 当前活动设计源中的既有草稿保持冻结，不继续精修，也不纳入提交。
3. R1-A01、R1-W01、R1-C01、R1-C02 不重启全量审计，只执行同样的能力覆盖门禁；已直接复用或职责明确的页面族快速判定为已承接。
4. 视觉规范只决定如何呈现能力，不替代产品能力裁决；代码当前缺口不再自动写成设计停止线。
5. F4-R 完成后，后续版本依照最新 family-ui、Radish 差异附录、正式代码和已确认代表页进行优化更新，除非产品形态或信息架构发生结构性变化，不从零重新设计。

## 7. 已确认决策

1. 普通帖子正式 Web 承接帖子 / 回帖点赞、reaction 和回帖的回帖。
2. 既有作者删除、投票和抽奖操作继续保留，分别作为作者状态与类型专属状态迁移，但不扩大普通帖子主画板。
3. 基础资料编辑、头像和显示时区进入正式 Private Web。
4. 转账、资产安全与统计不并入 F4-R，后续单独决定“迁移或退役”。
