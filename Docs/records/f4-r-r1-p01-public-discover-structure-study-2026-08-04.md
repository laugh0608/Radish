# F4-R R1-P01 公开社区发现结构研究

> 日期：2026-08-04（Asia/Shanghai）
>
> 状态：参考转译、公开能力审计与 PC 视觉裁决已完成；`R1-P01 / 社区发现 / PC 1440` 已确认为正式视觉基准
>
> 范围：只读审计、结构研究、Pencil 视觉收口与设计源清理；不修改 `/discover`、API、数据库、migration 或运行时 token

## 1. 结论

`R1-P01` 不能继续以“帖子长流 + 辅助 rail”为骨架。当前代码已经具备问答 / 投票、标签、Docs、商品和公开榜单等可独立读取的摘要能力，足以完成结构比较；最终混合信息流新增的公共频道摘要、成员公开短动态和跨帖神评集合则必须在实现前补统一公开读模型，不能由客户端临时拼装或伪造。

本轮三个候选均只使用现有公开读能力，并共同遵守：

- 首个主要视区并置至少三类真实社区实体；
- 保留一个明确主区，但帖子不占据绝大多数面积；
- 分类只作为紧凑导航或上下文，不使用全宽分类浏览大块；
- 不引入公开圈子、在线成员、跨实体时间流或独立作者推荐等尚无公开集合契约的能力；
- 候选通过结构复核后只保留当前已确认的代表设计，不让研究容器、说明板或未选方案继续干扰正式页面审核；mobile 未确认前不保留旧移动稿占位。

## 2. 参考结构转译

| 参考 | 观察到的结构关系 | 转译到 `/discover` | 明确不复制 |
| --- | --- | --- | --- |
| `13` 订单履约 | 单一主对象占据连续工作面；状态、进度、明细行使用不同尺度但保持一条任务轴 | 让一条结构化社区事件成为主区，例如待回答问题或进行中投票；讨论、参与人数和状态围绕主对象组织 | 后台侧栏、订单字段、履约步骤和外部配色 |
| `16` 数据源向导 | 大型选择区、紧凑 stepper、状态条和表单区形成明显尺度差；完成状态可被快速扫描 | 用大、中、小三档模块区分“正在发生”、知识 / 商品和主题 / 人员线索，状态进入实体卡而不是另起说明板 | 向导流程、数据库品牌、蓝色主操作和等尺寸选择卡网格 |
| `18` 日历工作台 | 大标题、紧凑视图工具与大面积主工作区形成稳定主次；侧栏只承担快速定位 | 公共头部之后直接进入“社区发现”工作面，搜索 / 切换保持紧凑，主内容区获得绝对视觉主导 | 后台左侧导航、日历业务、描述性副标题和紫色品牌表达 |
| `27` 客服协作 Inbox | 人员 / 状态、列表和详情三种实体关系同时可见；各列密度与视觉重量不同 | 将人员 / 榜单线索、结构化内容和知识 / 激励对象并置；允许窄列，但每列仍是社区内容而非后台导航 | Inbox 导航、AI Agent、在线 / 语音状态、聊天业务和外部纸纹背景 |

跨图共同结论：采用非对称主次、异构模块尺度、连续工作面和紧凑工具区；拒绝同尺寸卡片墙、后台式常驻导航、全宽分类板和单一帖子长流。

## 3. 当前公开能力审计

### 3.1 可直接组合

| 实体 / 模块 | 现有读能力 | 摘要字段与状态 | 公开路由 / 失败边界 | 结构用途 |
| --- | --- | --- | --- | --- |
| 最新 / 热门帖子 | `GET /api/v1/Post/GetList`，`postType=all`，支持 `newest / hottest / essence` | 标题、摘要、分类、标签、作者、互动计数、置顶 / 精华及更新时间 | `/forum`、`/forum/post/:id`；接口 `[AllowAnonymous]`，空态与失败可局部隔离 | 只保留少量讨论行，不再承担整页骨架 |
| 问答 / 投票 / 抽奖 | 同一列表接口使用 `postType=question / poll / lottery`；问答和投票具有专用排序 / 状态筛选 | 待解决 / 已解决、回答数、投票数 / 截止状态、参与人数 / 开奖状态 | `/forum/question`、`/forum/poll`、`/forum/lottery`；详情继续进入真实帖子路径 | 适合作为“正在发生”的主对象或次主对象 |
| 分类 | `GET /api/v1/Category/GetTopCategories` | 名称、slug、说明、图标、封面、帖子数和启用状态 | `/forum/category/:id`；接口 `[AllowAnonymous]` | 仅作紧凑入口或当前内容上下文 |
| 标签 | `GET /api/v1/Tag/GetHotTags`、`GetFixedTags`、`GetRelated` | 名称、slug、说明、颜色、帖子数、固定状态 | `/forum/tag/:slug`；公开失败不应拖垮其他模块 | 适合主题条、筛选入口和相关线索 |
| Docs | `GET /api/v1/Wiki/GetList` / `PublicGetList` | 标题、slug、摘要、封面、发布时间、版本和公开可见性 | `/docs`、`/docs/:slug`；匿名只得到可公开内容 | 适合一至两条“知识新页”，不伪造作者信息 |
| 商品 | `GET /api/v1/Shop/GetProducts` | 名称、图标 / 封面、类型、价格、折扣、销量和库存状态 | `/shop/products`、`/shop/product/:id`；接口 `[AllowAnonymous]` | 适合紧凑“热门好物 / 社区激励”对象 |
| 公开榜单 | `GET /api/v1/Leaderboard/GetTypes`、`GetLeaderboard` | 类型、排名、公开用户身份 / 商品、主次统计值 | `/leaderboard`；只允许经验、发帖、评论、人气、热门商品五类白名单 | 可提供人员 / 贡献者或热门商品的真实社区线索 |
| 作者线索 | 帖子 `PostItem` 作者 / 最近参与者，或用户类公开榜单 | PublicId、名称、头像、装扮、榜单指标 | `/u/:identifier`；依赖上游帖子或榜单的既定语义 | 可嵌入对应模块，不能伪装成独立作者推荐算法 |

### 3.2 只有入口或单对象读取，不足以成为独立首页模块

| 能力 | 当前边界 | 裁决 |
| --- | --- | --- |
| 公开用户资料 | `GetPublicProfile / Stats / Posts / Comments` 都需要已知 `identifier`，没有公开作者集合接口 | 只从帖子或榜单进入公开主页；不创建“推荐作者”模块 |
| `/circle` | `UserFollowController` 与关系流均要求登录，内容属于当前用户的私域关系链 | 只可作为登录后导航，不在匿名首页展示圈子摘要或动态 |
| 公共聊天室 | `ChannelController / ChannelMessageController` 整体要求登录；`Public` 仅表示所有登录用户可见，不等于匿名公开摘要 | 可作为未来首页对象，但必须先定义匿名 / 轻登录可见范围、频道摘要和消息摘录边界 |
| 神评 | 帖子详情已经公开展示当前神评 / 沙发，`CommentHighlight` 也有稳定快照；当前没有跨帖聚合的公开神评集合 | 可从既有高亮事实建立精选项，但必须新增跨帖公开查询、稳定排序和回源契约 |
| 公开宠物 | 只随已知用户的公开资料返回单张宠物卡，没有公共宠物目录 | 可在公开个人页展示，不进入本轮首页候选 |
| Forum / Docs / Shop / 榜单入口 | 各自已有完整集合页 | 首页只提供摘要与交接，不复制完整筛选和分页 |

### 3.3 必须新增公开读模型后才可成立

- 按统一排序混排帖子、问答、公共频道话题、成员公开短动态和神评的“社区正在发生”读模型；
- 成员“公开朋友圈”式短内容对象、公开资格、附件可见性、删除 / 屏蔽和治理契约；当前 `/circle` 只聚合关注作者的论坛帖子，不存在独立短动态对象；
- 有独立选择标准、去重和解释的“推荐作者 / 活跃成员”；
- 公开圈子目录、圈子动态或跨关系链推荐；
- 在线成员、Active Now、聊天室活跃度等实时 presence；
- 跨实体统一搜索、个性化、推荐解释、置顶和续读分页；
- 需要一次请求返回全部首页模块并统一版本 / 缓存语义的聚合首页读模型。

“社区正在发生”已经作为页面级视觉目标进入 Pencil，用于确认信息类型、密度和扫描结构；它不改变上述接口事实，也不是可直接实现的 API 契约。实现前必须单独设计公共频道摘要、公开短动态、跨帖神评聚合、统一游标、公开资格、隐私、稳定排序、失败降级和缓存语义，不能在 `PublicDiscoverApp.tsx` 中继续堆临时拼装规则。

## 4. 低保真候选

| 候选 | 主结构 | 首视区实体 | 当前契约 | 主要风险 |
| --- | --- | --- | --- | --- |
| 社区脉搏 | 左侧“正在发生”主区 + 少量最新讨论；右侧贡献者、知识和商品形成异构上下文 | 问答 / 投票、讨论、作者 / 榜单、Docs、商品、标签 | 全部可直接组合 | 右侧若继续增项会重新退化为辅助 rail 堆叠 |
| 多元拼图 | 顶部一个结构化主对象，其他实体以大中小块穿插；底部保留紧凑讨论与主题 | 问答 / 投票、Docs、商品、榜单、标签、讨论 | 全部可直接组合 | 容易卡片化，需要保留连续工作面和明确主区 |
| 社区长廊 | 以横向内容带组织“参与—知识—激励”，每带内部使用非对称大小 | 问答 / 投票、讨论、Docs、商品、榜单、标签 | 全部可直接组合 | 容易接近编辑式首页，mobile 重排顺序需要额外谨慎 |

`2026-08-04` 用户选择“社区脉搏”，同时指出首版 `1120px` 研究板在 PC 浏览器语境中使全部元素显得偏大。候选先重校准为 `1440px` 预览、约 `1392px` 主内容区和约 `860 / 518` 的主区—上下文区，并收紧标题层级、控件、圆角与间距；随后根据“信息密度过低、页面空旷”的反馈，将最新讨论、社区贡献者和热门主题各扩为 `5` 条连续扫描项，同时压缩知识 / 商品对象高度。

第三轮反馈进一步标出了主列中段的横向空白。根因不是内容条数，而是标题和作者信息全部左对齐、动作和箭头远置右侧，约 `860px` 主列缺少可扫描的中段信息。修订后，主问题使用“正文 + 问题脉搏”双栏，右侧只展示回答数、关注数和最近回答；五条讨论统一为“标题 / 作者 + 分类 + 互动 + 更新时间 + 箭头”的多列行。以上均来自现有 `PostItem`、问答状态或公开列表字段，不新增首页 API，也不通过放大元素填空。

结构获得认可后，获选 PC 页面已从研究容器提升为无外框的 `1440px` 顶层页面；对应 `390px` mobile 页面按“搜索—待回答问题—最新讨论—贡献者—知识 / 商品—主题”重排，不把 PC 右栏机械堆叠为单列。索引 / 说明板、旧 PC / mobile、独立关键状态、未选候选和研究外框均已删除，当时活动文件只保留两张业务页面与 `8` 个必要组件母版。

用户随后认为该稿仍缺少参考 UI 的直接气质。本轮重新逐张查看 `13 / 16 / 18 / 27`，并一度制作 `ref-27 × ref-13` 四栏直接复刻稿，用于验证窄导航、列表—详情和状态进度关系。用户明确否决该稿后，画板已从活动设计源删除，不再作为比较或恢复候选。

随后新增一张不覆盖原 PC / mobile 基线的 `1440 × 900`“参考重校准原创稿”。它不沿用外部产品的四栏骨架，只提炼 `ref-18 / 27` 的紧凑标题工具区与连续工作面、`ref-13` 的状态进度和行式指标，再围绕 Radish 现有公开对象重组为两个业务区。用户仍认为该稿只有内容密度，没有参考 UI 的布局紧凑与精致度；该画板也已删除，不再作为候选。

第三次复读在原 `13 / 16 / 18 / 27` 之外补看 `21 / 23 / 26`，一度把差异落实为 `232px` 固定侧栏、`60px` 顶栏、紧凑工具控件和连续讨论行。用户随后明确指出：目标不是这些参考产品的整体布局，而是其现代、舒适、自然并略带科技感的视觉语法；固定侧栏稿因此同样废弃，不再作为候选。

当前“现代自然视觉稿”恢复 Radish 自己的顶部公共导航和主区—洞察区信息架构。`1440 × 900` 页面使用 Geist 无衬线排版、`10–16px` 克制圆角、极轻阴影和小面积状态色；主区保留一条结构化问题和一组连续社区信息，洞察区组织社区脉搏、贡献者、知识与主题，并把热度、增量和参与信息嵌入内容本身，而不是生成独立 Dashboard。用户认可整体方向后，页面由临时 `default` 主题切换到 `guofeng` 语义主题：灰玉 `#5d6c57` 用于品牌识别，墨蓝 `#435c74` 用于主操作，国风暖白 `#f4efe6 / #fbf7f0` 用于页面与浮起表面。画布无裁切、溢出或失效引用，Pencil 保存与 `2x` PNG 导出检查通过。

局部复核继续暴露两个“结构正确但气质仍旧”的区域：最新讨论仍依赖五条等高行和通栏分割线，像后台列表；社区贡献者仍是五条同权排名，人员关系和贡献主次不够自然。修订后，讨论区使用柔底列表槽承载五条独立圆角行，以人物首字、讨论标题、作者 / 类型、单行摘要、回复簇和时间共同形成 Inbox 式扫描；贡献者区把前三位组织为高低错落的 spotlight，另外两位收为次级成员条。两处只改变视觉组织，不增加新的公开数据能力。

后续复核又移除了两处为填充版面而引入的图表语法。主问题右侧不再展示“过去 60 分钟热度”和回答 / 收藏 / 分享统计，改为从问题正文提炼搜索入口、标签组织和回访路径三个参与方向；社区脉搏的三个现有指标继续保留，但粗柱图改为近 `14` 天活跃热力点阵和较上周趋势。前者帮助用户理解讨论，后者只承担轻量趋势提示，不把社区首页变成分析 Dashboard。

最终内容复核指出连续五行虽然视觉成立，语义仍被“最新讨论”限制为帖子列表。当前区域已改名为“社区正在发生”，在同一紧凑扫描结构中并置公共频道话题、成员公开动态、跨帖神评、帖子和问答，并分别使用频道参与数、动态回应数、神评赞同数、帖子回复数和问答回答数表达对象差异。帖子与问答可复用既有公开读能力；公共频道、公开短动态和跨帖神评集合仅为长期产品目标，进入代码前必须按 3.2 / 3.3 补正式公开读模型。

用户最终确认该方向后，画板正式命名为 `R1-P01 / 社区发现 / PC 1440`。活动设计源删除旧“社区脉搏”PC / mobile、四栏直接复刻、双区原创、固定侧栏紧凑稿及其他失败研究，当前只保留唯一正式 PC、`8` 个必要组件母版和主题变量；Git 继续承担历史追溯。最终 PC 无裁切、溢出或失效引用，文件已保存并完成 `2x` PNG 导出检查。

## 5. 停止线与下一步

1. `R1-P01 / 社区发现 / PC 1440` 已确认为正式 PC 视觉基准；被否决的旧 PC / mobile 与所有失败稿不再恢复，后续只从 Git 历史追溯。
2. 关键状态不复制为第三张完整页面，继续继承共享 `State Slot` 组件语义，并在实现与真实截图阶段验证。
3. 下一轮据此独立设计 mobile，并为公共频道、公开短动态和跨帖神评补统一公开读模型、公开资格、隐私、稳定排序、游标分页与缓存边界；PC / mobile 共同通过后，才规划 `/discover`、`publicSeoStatic.test.ts`、locale 文案和灰玉运行时 token 的成组实现。
4. 本批不启动服务、不执行真实 smoke，不进入 `R1-P02`、Flutter、WebOS 或 Tauri。
