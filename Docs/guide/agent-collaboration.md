# Agent 协作与执行规则

本文承接 `AGENTS.md`、`CLAUDE.md` 不适合启动时全量加载的协作细则。根入口只保留跨任务、跨阶段且必须立即生效的长期约束；当前状态仍以[当前进行中](/planning/current)为准，技术契约仍以对应专题文档为准。

## 1. 文档职责与优先级

### 1.1 三层职责

| 层级 | 职责 | 典型内容 |
| --- | --- | --- |
| 根入口 | Agent 启动即生效的长期契约 | 授权边界、协作原则、核心红线、任务路由 |
| Docs 专题 | 稳定但按任务读取的详细规则 | 架构、接口、验证、配置、视觉、协作流程 |
| 当前规划与记录 | 会随阶段变化的状态和事实 | 当前顺位、临时门禁、“当前不做”、批次证据 |

根入口不是项目手册的副本，`Docs/README.md` 也不是阶段规则正文。短入口负责告诉读者“去哪里读”，专题文档负责解释“规则是什么”，规划与记录负责说明“现在处于什么状态、已经发生了什么”。

### 1.2 判断顺序

1. 先遵循项目所有者在当前任务中的明确要求。
2. 再遵循 `AGENTS.md` / `CLAUDE.md` 的启动级约束。
3. 根据任务路由读取当前 `Docs/` 真相源。
4. 通过当前代码、测试、配置和验证结果确认实现事实。
5. 文档与实现不一致时，不静默选择一方；先判断哪一侧过期，并在当前范围内收口口径。

## 2. 任务推进流程

### 2.1 开始任务

- 先确定任务属于回答、诊断、设计、实现、验证还是发布，不从一个请求推导出范围外的写入或外部操作。
- 只读取根入口路由到的必要文档；需要追溯事实时再进入 records、changelog 或 archive。
- 涉及当前阶段、优先级或下一顺位时，默认先读 `Docs/planning/current.md`；不足以判断阶段边界时再读 `Docs/development-plan.md`。
- 只有发生阶段边界、多端路线或壳层归属争议时，才继续读取相应阶段或前端专题。

### 2.2 方案与批准

- 架构、规则、接口、依赖、运行时行为或范围不清的变更，在实施前说明目标、边界、影响和验证方式并等待批准。
- 小规模、低风险、需求明确的文档、配置或清理变更可以直接实施。
- 不同合理解释会造成明显不同的用户行为、数据模型、兼容边界或外部影响时，先澄清再修改。
- 已批准方案若出现实质性范围变化，应暂停扩张并重新确认，而不是把变化隐藏在实现细节中。

### 2.3 实现与收口

- 优先治理根因和同类问题，避免只修复一个表象后留下重复缺陷。
- 不做玩具式最小实现、占位逻辑或无法覆盖主要使用路径的半成品。
- 不做与当前目标无关的重构；遇到直接影响需求的结构问题时，进行必要且边界清楚的修正。
- 抽象必须服务于真实复用、边界隔离、复杂度下降或契约稳定；简单逻辑不通过多层包装制造间接性。
- 错误处理只覆盖明确的输入、IO、网络、权限、并发和兼容风险，不吞异常、不伪造成功、不用默认值掩盖契约问题。
- 交付时说明完成内容、验证结果和仍未验证的真实风险，不把未执行的运行态验证写成已通过。

## 3. 设计先行与文档分层

- 长期功能、重要页面、跨模块能力或阶段性目标进入代码前，应先确认对应专题文档存在且边界清楚。
- 总体规划只承载方向、阶段、优先级和下一顺位，不承载具体功能的长期实现细节。
- 架构、前端、Guide 和 Features 专题承载定位、入口归属、停止线、数据模型、接口契约与验证口径。
- 模块说明承载具体页面流程、API 使用、迁移入口、前后端协作点和测试入口。
- records、changelog 和 archive 只记录批次事实、验证证据、历史流水和交接信息，不作为功能设计主文档。
- records、changelog 和其他带日期的协作记录统一使用 Asia/Shanghai（UTC+8）口径。
- 小规模 bug、低风险文案或样式调整、纯清理和不改变功能边界的验证补漏，不强制新建专题；若暴露说明与实现不一致，应同步修正真相源。
- 文档拆分、篇幅与索引规则统一遵循[文档篇幅治理](/guide/document-governance)。

## 4. 开发节奏与个人开发者阶段

### 4.1 生命周期节奏

- 产品正式上线并进入稳定运营前，默认采用主动批量验收、成组修复和一次性交付结论；应按链路矩阵主动复核、补测试和收口同类问题。
- 产品正式上线并由项目所有者确认进入稳定运营后，切换为小步修复、风险隔离、回归验证和发布留痕，避免在生产稳定期批量改动高风险链路。
- 当前处于哪种节奏只在 `Docs/planning/current.md` 声明；切换生命周期状态不需要改根入口。

### 4.2 功能推进与生产证据

- 仍有明确功能、维护、设计补全或可执行技术债时，继续推进这些工作，不以主动采集生产使用数据作为前置条件。
- 生产使用数据采集、长期行为聚合和主动反馈归因属于最终收尾事项；只有计划内主线已完整、没有明确任务可推进、产品进入最终完成体复核，并由项目所有者明确确认重启时，才允许重新开启。
- 不因观察周期到期、历史规划仍有记录、缺少真实使用证据或新会话重新评估，就主动排期或执行生产证据采集。
- 生产证据不足不得阻断功能设计、实现、测试、提交、发布或既有专题验收。
- 被动收到的明确生产故障、可追溯用户反馈或 `P0/P1` 可以直接进入维护线；处理具体问题不等于重启全链路主动采集。

## 5. 授权、运行与沙盒边界

### 5.1 依赖变更

- 执行 `dotnet add package`、`npm install`、`npm update` 或 `npm ci` 前，说明具体命令、目标版本以及对依赖声明和 lockfile 的影响，并取得当前任务授权。
- 授权只覆盖已经说明的命令和范围；新增包、改变版本策略或扩大 workspace 时重新确认。

### 5.2 服务启动与真实 Smoke

- 启动服务前，说明命令、端口、预计运行方式和清理方式，并取得当前任务授权。
- 不沿用上一轮或历史会话中的启动状态；真实 Smoke 前重新确认本任务所需前后端已经启动。
- Gateway 页面访问、PC / mobile 浏览器复核和 `check:host-runtime` 不作为普通连续开发的默认步骤，只在专题、阶段性任务或成组功能准备验收时，或项目所有者明确要求时执行。
- 具体入口、视图尺寸、状态覆盖和记录方式遵循[页面真实联调与浏览器 Smoke 规则](/guide/browser-smoke)。

### 5.3 沙盒与提权

- 构建、测试和最小验证默认先在沙盒内执行。
- 因权限隔离、PATH、网络或证书限制无法取得真实结果时，可以为必要验证申请最小范围提权。
- 提权不扩大任务授权；依赖安装、更新和服务启动仍必须先获得当前任务的明确许可。

## 6. 验证与留痕

- 开发中按风险执行定向测试、构建、类型检查、changed-only Lint、仓库卫生和 `git diff --check`，不为每个本地连续提交补完整回归记录。
- 准备合并到 `master` 时执行批次级 baseline、身份、依赖、范围和必要回归复核，并形成合并前证据。
- 发布或部署节点再补正式发布、运行态和回滚留痕；合并完成不等于自动授权 tag、镜像或生产部署。
- 验证命令、影响面判断和 CI 对齐以[验证基线说明](/guide/validation-baseline)为准。
- 当前阶段若有额外门禁，只在 `Docs/planning/current.md` 或对应阶段专题声明，不复制到根入口。

## 7. 根入口维护规则

### 7.1 允许进入根入口的条件

一条规则只有同时满足以下条件，才应加入 `AGENTS.md` / `CLAUDE.md`：

1. 跨任务成立，而不是某个功能或批次专属。
2. 跨开发阶段成立，不会随当前里程碑自然失效。
3. 必须在 Agent 读取专题文档前生效，否则容易产生高风险或大范围错误。
4. 无法只通过任务路由和对应 Docs 专题可靠承载。

不满足这些条件的内容，应归入专题、当前规划、记录或归档。

### 7.2 同步与验证

- 两个根入口只允许标题和首段入口名称不同，从第 4 行开始必须完全一致。
- `npm run check:docs` 会检查两份正文同步、文本卫生和 Markdown 本地链接。
- 修改根入口时应同步检查关联 Docs 是否仍为真相源；修改阶段状态或临时门禁时不应反向更新根入口。
- 根入口目标是保持短、稳定和可路由，而不是汇总所有项目知识。
