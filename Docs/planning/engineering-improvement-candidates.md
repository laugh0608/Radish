## 目标与选择依据

优先提高验证结论的可信度、关键业务可靠性与个人维护效率，再评估扩大功能和平台投入。每次选择一个边界明确的批次，说明它改善的用户任务或维护问题，避免同时启动全仓结构治理和多端扩张。

沿用既有产品分工：社区核心与知识 / 治理支撑优先，激励层完善已有正确性，多端能力按实际使用价值承接。主动生产数据采集继续冻结；选题可依据代码事实、已有反馈和代表用户任务，不以采集生产数据作为前置。

## 建议批次与完成标准

| 建议顺序 | 批次 | 当前状态 | 核心完成标准 |
| --- | --- | --- | --- |
| 1 | 类型检查入口与覆盖真实性 | 待确认；已记录缺口 | Client / Console 的 app 与 node 工程都被检查；故意引入类型错误可使入口失败 |
| 2 | Outbox 租约归属与迟到结果 | 待确认；静态保护缺口已定位 | 旧执行不能处理或提交新租约的结果，交接与迟到场景有定向测试 |

以上为工程建议顺序，不直接赋予生产事故等级。若发现新的实际故障，按既有维护线重新判断优先级。

### 1. 类型检查入口与覆盖真实性

- **事实来源**：审阅记录 R-01；Client 与 Console 根配置 `files: []`，普通 `tsc --noEmit` 不递归检查引用工程。Console strict 配置仅列出八个入口及其依赖。
- **建议范围**：先修正四个 Web workspace 的检查编排和本地 / CI 对齐，保留已有 build 行为；对 Console 全量 strict 的扩展单独按高风险模块推进。
- **验证方式**：输出或核对实际检查的文件集合，在隔离的临时副本中验证 app 与 node 类型错误都会导致失败；移除临时错误后检查全部通过。
- **完成标准**：脚本覆盖与验证手册一致，检查不以空工程成功冒充应用通过；清除验证手册中的对应已知限制并链接修复记录。
- **当前可用说明**：显式指定 app / node 配置的补充命令见[验证基线](/guide/validation-baseline)。补充命令不是已修复脚本的证据。

### 2. Outbox 租约归属与迟到结果

- **事实来源**：R-02；领取有租约，入队执行和结果提交未携带可校验的本次领取身份。
- **建议范围**：评审 Repository / Service / Hangfire job 的领取、执行与提交契约，确定租约标识或版本如何流转；检查既有消费者幂等边界。
- **必要场景**：旧任务排队超时、新任务接管、旧执行成功 / 失败晚到、同一旧 job 重复执行、租约恢复及正常重试。
- **完成标准**：只有当前领取方可以执行对应租约和提交结果；旧结果不更改新任务状态或覆盖重试次数；SQLite 与 PostgreSQL 的定向语义均有证据。
- **实施边界**：涉及接口和可能的迁移，先确认方案；不以延长超时替代归属校验，不扩为新的队列平台。方案需同时解释执行中租约到期与业务副作用幂等，不能仅在完成时检查状态。

### 3. Console 浏览器安全边界评审

- **事实来源**：R-03；Client / Console 都使用 `localStorage` 持有令牌，同源路径不能隔离这些数据。实际生产 origin 与安全响应头未核实。
- **建议先做**：盘点仓库部署拓扑、公开内容与管理端信任边界、令牌生命周期，以及 CSP / 上传内容等关联输入；外部部署读取按实际授权范围执行。
- **候选选项**：独立 Console origin、降低浏览器可读取令牌暴露、必要时评审服务端会话方案。比较 OIDC redirect、CORS、退出、续签与部署维护成本。
- **完成标准**：区分仓库默认、实际部署事实和假设；给出有限方案或明确风险接受、触发复核条件与验收场景。
- **实施边界**：本候选不是已确认的 XSS 漏洞，也不自动启动 BFF、域名变更或认证重构。

### 4. 公开 Web 加载依赖与性能预算

- **事实来源**：R-04；入口 HTML 显式引用的 JavaScript 约 `2.79 MB`，逐文件 gzip 估算约 `781 KB`，包含多个业务分块。
- **建议范围**：从匿名公开浏览的入口依赖图入手，核对路由懒加载、共享模块与 `manualChunks`，再选择具体优化点。
- **完成标准**：记录同一构建口径的前后体积、HTML 预加载依赖和进入后续页面的加载行为；预算数值在获选批次按基线与目标确认，不能通过提高告警阈值代替优化。
- **运行验证**：服务启动获授权后覆盖 PC / mobile，记录缓存、网络条件及真实浏览器指标；构建体积不表述为首屏时间或 LCP。
- **关联后置**：Flutter 字体与包体预算可以独立评审。现有字体与 UGC 回退契约保持，不按当前界面文案裁字，也不自动引入网络字体。

### 5. Flutter 自动化基础

- **事实来源**：R-05；本地 Flutter 验证记录已存在，通用 `Repo Quality` / `Candidate Quality` 尚未执行 Flutter analyze、test 或平台构建。
- **建议范围**：评估 Dart analyze / test 的自动入口、平台文件影响判定、runner 与工具链版本、缓存、执行成本和本地复现方式。
- **完成标准**：共享代码改动有共享验证，平台工程改动有对应构建验证；汇总能够明确区分通过、失败和未执行；本地与 CI 的范围一致。
- **实施边界**：不要求每个文档提交构建所有平台；不把无签名构建写成真机或分发验收。CI、依赖和工具链变更按既有规则分别确认。

### 6. 行为测试与维护热点治理

- **事实来源**：R-06；存在较多源码文本断言、大型服务 / 页面及可选业务依赖，详细样本见审阅记录。
- **建议首选行为**：身份切换后的请求隔离、登录过期后的提交恢复、编辑冲突保留、重复提交、权限变化、移动输入焦点与导航保护。
- **建议首选热点**：Post、Wiki、内容治理服务，以及公开帖子详情和 Flutter shell；按下一次真实修改触达选一个职责，不同时改造所有模块。
- **完成标准**：职责边界和必需依赖更明确，正常 / 失败 / 并发路径能独立验证；保留高价值静态守卫，但不把文本匹配当成交互测试。
- **实施边界**：不为减少行数机械切片，不以测试方便把必要业务依赖变成可选；不自动迁移 ORM、引入微服务或增加状态管理依赖。
- **Console strict**：权限、订单和治理页面优先逐步扩面，单独记录实际覆盖；不把 R-01 的命令修复误写成 Console 全量严格模式完成。
